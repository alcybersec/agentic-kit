## Order, and why

**M2.1 first, before any of the rest is built.** The two targets are materially unlike the three
fixtures, and surveying them already turned up things the fixtures cannot show:

- Both carry their own `.claude/` with `settings.json`, `skills/` and `commands/`; `study-helper-project`
  also has `.claude/rules/`, a Claude Code feature the kit knows nothing about.
- `321_project` has **uncommitted work** on a feature branch and 20 worktrees; `study-helper-project` has
  30. Retrofitting anywhere but a worktree would be reckless, which is why §9.4 says worktree.
- `study-helper-project`'s `CLAUDE.md` is **333 lines**. Merged under `## Project-specific notes` that
  becomes ~450, against Claude Code's own guidance of keeping it under 200.
- Their shapes are not the fixtures' shapes: `services/` holds 851 files in one, `src/` 292 with a
  separate `frontend/` in the other.

The audit's clearest lesson was that reading real rendered output found what the tests could not. Every
remaining item is a guess about what a real retrofit needs; doing the retrofit first replaces the guesses
with findings. `/kit-upgrade` in particular risks solving the wrong problem if built blind.

**Checked before starting**: both `.claude/agents/` directories are empty and neither project's skill
names collide with the kit's ten, so the roster and the skills can land without renaming anything.

## M2.1 findings — retrofit of `321_project`, 2026-10-03

Done in a fresh worktree (`~/Documents/coding/321_project-kit`, branch
`chore/agentic-kit-retrofit` off `main`, created after `git worktree list` showed 20 others and two
locked). The host checkout, its uncommitted work and all 20 worktrees were untouched throughout.

**§9.4's criteria, met:** the pre-existing 109-line `CLAUDE.md` is present **verbatim** under
`## Project-specific notes` with the kit's scaffolding above it; all 14 pre-existing `permissions.allow`
entries survive alongside the kit's 25; `/kit-doctor` reports every mechanical check green;
`/plan-status` read the generated spine correctly (milestone, next task, gates, risks, drift);
`/next-task` dispatched `architect`, which produced four real contracts derived from the code as it
stands, an ADR, a `decisions.md` row and 13 tests — and re-ran them itself, reporting the command and
`Ran 13 tests — OK`, having first confirmed they failed.

### Fixed in the kit as a result

1. **A role could never commit a file it created.** `git add` was in neither the allow nor the deny list,
   so it prompted; and `git commit --only <path>` cannot commit an untracked file. The kit mandates
   atomic commits and then forbade the only way to stage new work — on a task that produced a contracts
   document, an ADR and 13 passing tests, none of which could be committed. `Bash(git add:*)` is now
   allowed, which is safe because the four sweep forms are denied and deny is evaluated first.
2. **An unwritable target caused a partial install.** `321_project`'s `.claude/settings.json` is
   deliberately mode 444. The render merged `CLAUDE.md`, wrote an agent card, then failed with exit 4 and
   a half-installed tree — for a condition `os.access` reports up front. It is a preflight blocker now,
   so the run refuses with 3 and an untouched tree.

### Found, not yet fixed

3. **`spine.*` paths are not actually configurable.** `render()` hardcodes `docs/strategy.md` and
   `docs/design.md` while §5 presents them as profile fields; setting them to anything else renders the
   defaults and then fails verification. This bit immediately: `docs/strategy.md` is a poor name in a
   repository where "strategy" means trading strategy. Either the renderer should emit at the configured
   paths, or the schema should stop offering the choice. **M2.6 — fixed in 1.7.0**: the renderer emits
   at the configured paths, and the preserved set is resolved from the profile.
4. **The kit assumes the tracker and CI live on the same forge.** Here `origin` is the self-hosted GitLab
   and CI is `.github/workflows`. `forge.kind: gitlab` with that `ci` validates, but the rendered
   CLAUDE.md then tells the agent not to propose the other forge's CI system while `ci` points straight
   at it. Exclusivity should be about the tracker; CI location is independent. **M2.7 — fixed in
   1.7.0**: `exclusive` with the other forge's CI is now rejected, and CLAUDE.md states the split.
5. **`CLAUDE.md` and `.claude/` are gitignored in this project.** A reasonable, apparently deliberate
   choice — and it means the rendered role cards, lock and profile never travel to another worktree or
   another machine, so each worktree needs its own render, and `memory: project`'s "shareable via version
   control" is false here. The kit should say so rather than assume otherwise. **M2.8.**
6. **Unowned shared code is where the floors actually live.** The architect found that `src/contracts/`,
   `src/common/` (the event bus), `src/exchange/`, `src/sim/` and `src/modules/observability/` have no
   owner, and that two of the three floors depend on exactly that code. It raised R-001 itself. This is
   M2.4's check, found by a role agent reading the tree rather than by any tool — which is the argument
   for building it.
7. **A merged `CLAUDE.md` reaches 241 lines** here and would reach ~450 on `study-helper-project`,
   against Claude Code's own guidance of under 200. The merge is correct; the result is too long. Worth a
   note in the retrofit path, pointing at skills for the overflow.
